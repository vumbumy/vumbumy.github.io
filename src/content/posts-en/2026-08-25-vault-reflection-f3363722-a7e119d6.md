Two groups requested business metrics for different live dashboards. One wanted a combined view for each center. The other wanted live sales results.

The problem was not building the screens. I had to find a stable way to provide the numbers. The dashboards also needed frequent updates without querying the internal business system each time.

I reviewed both requests, the existing mockups, and code from related systems. I decided that reading data directly from the production server did not fit this work.

However, choosing a data path did not make the work ready for development. The groups still understood some shared metrics in different ways.

## The problem I owned

My task was to define which metrics the internal business system would provide and how it would provide them.

A separate existing system already handled call-related numbers. I therefore focused on metrics held by the internal system. These included work status and performance results.

The main limit was the load on the production system. Several screens needed updates close to real time without directly calling the production server.

Other layers would handle the screen layout and combine data. The internal system only needed to provide clear sources for the required metrics.

## Facts and limits I checked

I first reviewed the requirements in the static mockups and the existing dashboard code.

I then studied the internal system code indirectly. I matched each metric to its source data and related status values.

This showed that a value available in the system did not always match the meaning wanted by the business groups.

One example was a performance metric based on actual cases. The groups had not agreed on its definition. It could mean cases waiting for intake or cases waiting for an application.

The displayed number would change depending on which status was counted. The business definition had to be confirmed before writing code.

## The choice I made

I chose to provide the data through a statistics database, not the production server.

The reason was clear. More frequent dashboard checks or more user groups must not increase load on the internal business system. Avoiding direct calls to the production server became a design goal.

I also kept screen display and data combination outside the internal business system. A separate middle layer or the dashboard would handle this work.

The connection has not been added yet. I only chose the design direction for the data path.

## What I actually did

I separated the metrics needed for the two requests. I compared them with existing materials and data sources found in the internal code.

For each metric, I linked the original data with its status value. I then recorded which values the system could provide.

I excluded areas handled by other systems, such as call metrics.

When metric definitions conflicted, I did not choose one without agreement. I left them as questions for the business groups to confirm.

I also separated several items into later work. These included access to the statistics database and links between centers, work queues, and users. Access rules for different user types also remain.

## Confirmed results and remaining work

I confirmed the source data and related status values for each metric. I also chose a direction that uses the statistics database.

The boundary is now clear: the dashboard should not call the production server directly.

There is no completed system connection or dashboard result yet. The metric conflicts must be resolved, and data access must be approved before planning development.

Mappings between groups and users also remain. Access must also differ based on who views the dashboard.

Until these items are confirmed, the design direction cannot be treated as an implemented result.
