두 조직에서 각기 다른 실시간 현황판에 필요한 업무 지표를 요청했다. 한쪽은 센터별 통합 현황을, 다른 쪽은 영업 조직의 실시간 실적을 보고 싶어 했다. 해결해야 할 문제는 화면을 만드는 일이 아니었다. 현황판이 갱신될 때마다 내부 업무 시스템을 조회하지 않으면서도 필요한 수치를 안정적으로 제공할 경로를 정해야 했다.

나는 요청 두 건과 기존 목업, 관련 시스템의 코드를 함께 검토했다. 그 결과 운영 서버에서 직접 데이터를 가져오는 방식은 이번 작업의 목표와 맞지 않는다고 판단했다. 다만 데이터 경로를 정하는 것만으로 구현 준비가 끝난 것은 아니었다. 같은 지표를 두고도 현업에서 뜻을 다르게 이해하는 부분이 남아 있었다.

## 실제로 맡은 문제

내가 맡은 범위는 내부 업무 시스템이 현황판에 어떤 지표를 어떤 방식으로 제공할지 정리하는 일이었다. 통화 관련 수치는 기존의 별도 시스템이 담당하고 있었기 때문에, 이번 검토에서는 업무 처리 상태와 실적처럼 내부 시스템이 보유한 지표에 집중했다.

가장 큰 제약은 운영 부하였다. 여러 화면이 실시간에 가깝게 갱신되더라도 운영 서버를 직접 호출하지 않는 구성이 필요했다. 화면 구성이나 데이터 조합은 다른 계층에서 처리하고, 내부 시스템은 필요한 지표의 출처를 명확히 제공해야 했다.

## 확인한 사실과 제약

정적 목업에 적힌 요구사항과 기존 현황판 코드를 먼저 살폈다. 이어 내부 시스템의 코드를 간접적으로 분석해 각 지표가 어느 데이터에서 나오며 어떤 상태값과 연결되는지 대응시켰다. 이 과정에서 기술적으로 읽을 수 있는 값과 현업이 원하는 지표의 뜻이 항상 같지는 않다는 점을 확인했다.

실제 사례가 실적을 뜻하는 한 항목이었다. 이 수치를 접수 대기 상태로 볼지, 청약 대기 상태로 볼지 요청 조직 사이에서 정의가 정리되지 않았다. 어느 상태를 집계하느냐에 따라 화면에 표시되는 값이 달라지므로, 코드를 작성하기 전에 현업의 정의가 먼저 확정돼야 했다.

## 내가 한 선택

데이터는 운영 서버가 아니라 통계용 데이터베이스에서 읽어 제공하는 방향으로 정했다. 기준은 분명했다. 현황판의 조회 주기나 사용 조직의 증가가 내부 업무 시스템의 부하로 이어지지 않아야 했다. 운영 서버 직접 호출은 하지 않는 것을 목표로 삼았다.

화면 표시와 여러 데이터의 결합도 내부 업무 시스템의 책임으로 넣지 않았다. 별도 중계 계층이나 현황판 쪽에서 처리하도록 범위를 나눴다. 아직 연동을 적용한 것은 아니며, 데이터 제공 경로에 대한 설계 방향을 정한 단계다.

## 실제로 한 일

두 요청에서 필요한 지표를 나누고, 기존 자산에서 확인되는 항목과 내부 코드의 데이터 출처를 대조했다. 지표별 원본 데이터와 상태값을 연결해 어떤 값까지 제공할 수 있는지 정리했다. 통화 지표처럼 다른 시스템이 맡은 영역은 이번 범위에서 분리했다.

정의가 충돌하는 항목은 임의로 하나를 택하지 않고 현업이 확정해야 할 질문으로 남겼다. 통계용 데이터베이스의 접근 권한 확보, 센터와 업무 큐·사용자 사이의 연결, 관리자와 상담사 권한 구분도 후속 작업으로 분리했다.

## 확인된 결과와 남은 일

현재 확인된 결과는 지표별 데이터 출처와 상태값의 대응 관계, 그리고 통계용 데이터베이스를 거치는 제공 방향이다. 운영 서버를 직접 호출하지 않는다는 경계도 정리됐다.

아직 API 연동이나 실제 현황판 적용 결과는 없다. 지표 정의 충돌을 해소하고 데이터 접근 권한을 확보해야 구현 계획을 세울 수 있다. 조직과 사용자 매핑, 화면을 보는 사람에 따른 권한 분리 역시 남아 있다. 이 항목들이 확정되기 전까지는 설계 방향을 구현 성과로 볼 수 없다.
