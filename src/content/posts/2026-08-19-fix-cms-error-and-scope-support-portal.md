최근 맡았던 두 문제는 겉으로 전혀 달랐다. 하나는 이미지 업로드가 모두 실패하는 운영 장애였고, 다른 하나는 30개 탭으로 흩어진 고객지원 업무를 포털로 옮기는 기획이었다. 한쪽은 당장 복구가 필요했고, 다른 쪽은 범위와 담당 조직조차 정해지지 않았다.

두 일을 처리할 때 바로 코드를 고치거나 회의부터 열지는 않았다. CMS에서는 애플리케이션보다 먼저 데이터 구조를 확인했고, 포털에서는 담당 조직을 정하기 전에 시트에 담긴 실제 업무부터 분류했다.

## 실제로 맡은 문제

운영 중인 CMS에서는 콘텐츠 이미지를 올릴 때마다 500 오류가 발생했다. 이미지가 들어가지 않으니 새 콘텐츠 등록도 멈췄다. 운영팀의 업무가 막힌 상황이라 복구 속도가 중요했지만, 원인을 모른 채 코드를 수정하면 장애 시간을 더 늘릴 수 있었다.

고객지원 포털 요청은 다른 종류의 문제였다. 업무가 구글 시트 30개 탭에 흩어져 있었고, 무엇을 포털로 옮길지 정해지지 않았다. 고객관리 시스템에 포함할 기능과 별도 경량 도구로 둘 기능의 경계도 모호했다. 개발을 맡을 조직까지 함께 결정해야 했다.

## 확인한 사실과 제약

CMS는 이미지 업로드 코드를 먼저 의심하기 쉬운 상황이었다. 하지만 Wagtail의 저장 구조를 확인해 보니 이미지는 최상위 Collection 노드가 있어야 정상적으로 저장된다. 데이터베이스 마이그레이션 과정에서 이 루트 레코드가 빠졌고, 애플리케이션 로직이 아니라 데이터 구조가 깨진 상태였다.

포털은 요청서만 읽어서는 범위를 정할 수 없었다. 30개 탭을 직접 열어 중복 업무, 자동화할 수 있는 업무, 사람의 판단이 필요한 업무를 구분했다. 그 결과 어떤 기능을 고객관리 시스템 안에 두고 어떤 기능을 별도 도구로 제공할지 논의할 기준이 생겼다.

## 내가 한 선택

CMS에서는 코드 수정과 재배포를 하지 않았다. 애플리케이션 로직은 정상이었고 누락된 데이터만 보정하면 됐기 때문이다. 가장 빠른 복구 경로로 루트 Collection 레코드를 되살리는 SQL 긴급 패치를 선택했다.

포털에서는 어느 조직이 맡을지 먼저 묻지 않았다. 업무 범위가 불명확한 상태에서는 담당 조직도 판단하기 어렵다고 봤다. 시트 분석 결과를 기능과 메뉴 구조로 바꾸고, 그 자료를 바탕으로 개발 책임을 결정받는 순서를 택했다.

## 실제로 한 일

CMS 데이터베이스에 누락된 루트 Collection 레코드를 보정한 뒤 이미지 업로드가 다시 동작하는지 확인했다. 별도의 애플리케이션 변경 없이 정상화되는 것을 확인했고, 같은 누락이 반복되지 않도록 스키마 구성 절차에 루트 Collection 생성을 포함했다.

포털은 30개 탭의 내용을 분류한 뒤 실제 서비스에서 검토할 수 있는 메뉴 그룹과 기능 경계로 정리했다. 단순한 탭 목록이 아니라 어떤 기능을 기존 시스템에 넣고 어떤 기능을 가볍게 분리할지 비교할 수 있는 형태로 만들었다. 이후 이 자료를 의사결정권자에게 전달해 담당 조직과 진행 방향을 결정하도록 요청했다.

## 확인된 결과와 남은 일

CMS는 이미지 업로드와 콘텐츠 등록이 다시 가능해졌다. 장애 원인이 코드가 아닌 마이그레이션 과정의 데이터 누락이라는 점도 확인했다. 복구에서 끝내지 않고 초기 데이터 생성 절차까지 보완했다.

포털은 30개 탭이라는 막연한 요청에서 벗어나 메뉴와 기능 단위로 검토할 수 있는 상태가 됐다. 개발 범위와 담당 조직을 논의할 자료가 생겼지만, 실제 구현과 단계별 전환은 이후 작업으로 남았다.

두 사례에서 실제로 한 일은 거창한 방법론을 만드는 것이 아니었다. 장애에서는 코드와 데이터 중 어디가 깨졌는지 확인했고, 기획에서는 조직을 정하기 전에 업무 범위를 먼저 펼쳐 봤다. 무엇을 고치고 무엇을 결정해야 하는지 구체화한 뒤에야 다음 조치를 선택할 수 있었다.
